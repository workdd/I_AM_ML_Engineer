두 순위의 융합과 prefilter gate, 실행 증거 기반 보고를 본다.

## RRF 융합과 prefilter gate

Reciprocal Rank Fusion 은 점수의 척도를 맞추지 않고 순위만 더한다. BM25 점수와 L2 거리는 단위가 다르므로 순위로 합치는 편이 단순하다. Omnigraph의 식은 다음과 같다. 순위 $r$ 은 1부터 센다.

$$
\mathrm{rrf}(e) = \sum_{a \in \{\text{primary}, \text{secondary}\}} \frac{1}{k + r_a(e)}
$$

arm 에 없는 entity 는 그 arm 의 항이 0 이다. 기본 `k` 는 60 이고 0 이나 U32 범위 밖의 값은 거부한다 ([search.rs L402-L411](https://github.com/ModernRelay/omnigraph/blob/00b8cca842f2bf009bebeefcf765672b5ff64b26/crates/omnigraph/src/engine/search.rs#L402-L411)).

### 코드 분석: `fuse_arms`

`crates/omnigraph/src/engine/graph.rs` [graph.rs L151-L165](https://github.com/ModernRelay/omnigraph/blob/00b8cca842f2bf009bebeefcf765672b5ff64b26/crates/omnigraph/src/engine/graph.rs#L151-L165)

fused 점수 계산을 본다.

```rust
    let k = rrf.k as f64;
    let scored: Vec<(String, f64)> = all_ids
        .iter()
        .map(|id| {
            let p = primary_rank
                .get(id)
                .map(|&r| 1.0 / (k + r as f64 + 1.0))
                .unwrap_or(0.0);
            let s = secondary_rank
                .get(id)
                .map(|&r| 1.0 / (k + r as f64 + 1.0))
                .unwrap_or(0.0);
            (id.clone(), p + s)
        })
        .collect();
```

`r` 은 0부터 세는 순위이므로 `+ 1.0` 이 식의 1부터 세는 순위가 된다. 순위는 행이 아니라 entity 기준이다. [graph.rs L125-L142](https://github.com/ModernRelay/omnigraph/blob/00b8cca842f2bf009bebeefcf765672b5ff64b26/crates/omnigraph/src/engine/graph.rs#L125-L142) 은 id 가 처음 나온 위치만 순위로 기록한다. 한 entity 가 순회 때문에 여러 행으로 펼쳐져도 순위는 하나이고, 출력에서는 그 entity 의 모든 행이 같은 fused 점수를 받는다. `limit` 은 여기서 자르지 않고 위의 `Sort` 가 자른다. 결과 열은 `fused_schema` 가 arm 의 열 뒤에 `F64` 하나를 덧붙인 형태다. 연산자 테스트는 두 arm 모두 1위인 entity 의 점수가 `2.0 / 61.0` 임을 확인한다.

융합 연산자 `RankFuseExec` 는 [rank_fuse.rs L34-L45](https://github.com/ModernRelay/omnigraph/blob/00b8cca842f2bf009bebeefcf765672b5ff64b26/crates/omnigraph/src/engine/operators/rank_fuse.rs#L34-L45) 에 있다. 두 arm 을 모두 모은 뒤 [rank_fuse.rs L105-L147](https://github.com/ModernRelay/omnigraph/blob/00b8cca842f2bf009bebeefcf765672b5ff64b26/crates/omnigraph/src/engine/operators/rank_fuse.rs#L105-L147) 의 `ranked` 로 각 arm 을 점수, 융합 binding 의 id, 하위 행 키 순으로 정렬한다. 같은 점수의 entity 가 실행마다 같은 순위를 받게 하려는 정렬이다. 정렬 연산자 일반은 6장에서 다룬다.

### prefilter gate

`rrf` 의 `bm25` arm 은 상한이 없으므로 말뭉치 전체를 채점한다. 순회가 순위 binding 을 소수의 entity 로 좁히는 쿼리라면 전체 채점은 낭비다. gate 는 실행 전에 순회의 첫 hop 을 만족할 수 있는 entity 의 상위 집합을 계산해 `id IN (...)` 으로 스캔에 넣을지 결정한다.

| 설정 | 기본값 | 의미 | 코드 |
|---|---|---|---|
| `OMNIGRAPH_RRF_GATE_RATIO` | 0.10 | 적격 수가 type 행 수의 이 비율 이하일 때 prefilter | `DEFAULT_GATE_RATIO` |
| `OMNIGRAPH_RRF_GATE_MAX_IDS` | 100,000 | 적격 수 절대 상한 | `DEFAULT_GATE_MAX_IDS` |
| `rrf_plan` (`OMNIGRAPH_RRF_PLAN`) | `auto` | `force_prefilter`, `force_postfilter` 는 진단용, `process` 범위 | [settings.rs L69-L76](https://github.com/ModernRelay/omnigraph/blob/00b8cca842f2bf009bebeefcf765672b5ff64b26/crates/omnigraph-compiler/src/settings.rs#L69-L76) |
| `ann_nprobes` (`OMNIGRAPH_ANN_NPROBES`) | 20 | partition 상한, `0` 은 무제한, `request` 범위 | [settings.rs L93-L100](https://github.com/ModernRelay/omnigraph/blob/00b8cca842f2bf009bebeefcf765672b5ff64b26/crates/omnigraph-compiler/src/settings.rs#L93-L100) |

두 비율 값은 [plan_source.rs L90-L108](https://github.com/ModernRelay/omnigraph/blob/00b8cca842f2bf009bebeefcf765672b5ff64b26/crates/omnigraph/src/engine/plan_source.rs#L90-L108) 에서 계획 시점에 한 번 읽혀 계획의 `GatePolicy` 로 실린다. 해석할 수 없는 값은 기본값이 된다.

### 코드 분석: 적격 집합 계산

`crates/omnigraph/src/engine/search.rs` [search.rs L624-L640](https://github.com/ModernRelay/omnigraph/blob/00b8cca842f2bf009bebeefcf765672b5ff64b26/crates/omnigraph/src/engine/search.rs#L624-L640)

적격 entity 를 세고 문턱을 판정하는 부분을 본다.

```rust
    let passes = |dense: u32| {
        adjacencies.iter().all(|(out, incoming)| {
            out.is_some_and(|adj| adj.has_neighbors(dense))
                || incoming.is_some_and(|adj| adj.has_neighbors(dense))
        })
    };
    let eligible_count = (0..idx.len() as u32).filter(|&dense| passes(dense)).count() as u64;
    if eligible_count == 0 {
        return fall_back(RrfGateFallback::EmptyEligible, Some(0));
    }
    if !forced {
        let ratio_ok = corpus > 0 && (eligible_count as f64) <= policy.ratio * (corpus as f64);
        let cap_ok = eligible_count <= policy.max_ids;
        if !(ratio_ok && cap_ok) {
            return fall_back(RrfGateFallback::Threshold, Some(eligible_count));
        }
    }
```

적격 조건은 필수 첫 hop 마다 해당 방향의 이웃이 하나라도 있는 것이다. 이 판단은 엣지 table 을 읽지 않고 메모리의 adjacency index 에서 한다. `GraphIndex` 는 [mod.rs L168-L177](https://github.com/ModernRelay/omnigraph/blob/00b8cca842f2bf009bebeefcf765672b5ff64b26/crates/omnigraph/src/graph_index/mod.rs#L168-L177) 에서 node type 별 dense id 사전과 엣지 type 별 CSR(나가는 방향), CSC(들어오는 방향)를 가진 위상 전용 index 이고, [mod.rs L120-L124](https://github.com/ModernRelay/omnigraph/blob/00b8cca842f2bf009bebeefcf765672b5ff64b26/crates/omnigraph/src/graph_index/mod.rs#L120-L124) 의 `has_neighbors` 는 offset 두 개를 비교하는 O(1) 연산이다. 개수를 먼저 세고 문턱을 통과한 경우에만 id 문자열을 만든다. 넓은 순회에서는 id 목록을 할당하지 않는다.

`GraphIndex` 는 `optimize` 가 객체 저장소의 `__graph_index/csr-current.bin` 에 저장해 두고([persist.rs L137-L142](https://github.com/ModernRelay/omnigraph/blob/00b8cca842f2bf009bebeefcf765672b5ff64b26/crates/omnigraph/src/graph_index/persist.rs#L137-L142)), 쿼리는 이를 읽기만 한다. `load` 는 엣지 table 마다 `TableStamp` 를 현재 snapshot 과 대조하고, 없거나 낡았거나 digest 가 맞지 않으면 메모리 빌드로 돌아간다. 순회 연산자가 이 index 를 쓰는 방식은 6장에서, 저장 형식은 8장에서 다룬다.

### 답이 같은 두 계획

[search.rs L449-L476](https://github.com/ModernRelay/omnigraph/blob/00b8cca842f2bf009bebeefcf765672b5ff64b26/crates/omnigraph/src/engine/search.rs#L449-L476) 의 주석은 `rrf_prefilter_gate` 의 불변식을 적는다. prefilter 계획과 postfilter 계획은 BM25 점수 동률을 제외하면 답이 같아야 하고, 추정치는 비용만 바꿀 뿐 답을 바꾸면 안 된다.

| 울타리 | 이유 |
|---|---|
| 적격 집합은 순회 생존자의 상위 집합 | 부분 집합이면 답이 바뀜 |
| 전문 index 가 모든 fragment 를 덮을 때만 | 덮지 않은 fragment 는 필터에 따라 점수가 변함 (`coverage_admits`) |
| `rrf` 의 `nearest` arm 은 prefilter 하지 않음 | `k` window 가 적격 집합에 따라 달라짐 |
| 빈 적격 집합은 postfilter | 같은 빈 join, `IN ()` 의미 회피 |
| 실패하는 단계는 postfilter 로 후퇴 | 최적화 실패가 쿼리 실패가 되지 않음 |

단독 `nearest` 는 [search.rs L663-L739](https://github.com/ModernRelay/omnigraph/blob/00b8cca842f2bf009bebeefcf765672b5ff64b26/crates/omnigraph/src/engine/search.rs#L663-L739) 의 `nearest_prefilter_gate` 를 쓴다. `nearest` 의 후보 window 는 적격 집합에 따라 달라지므로 여기서는 답이 같지 않다. 대신 순회가 도달하는 entity 만 순위를 매기는 것이 이 쿼리의 계약이므로 prefilter 가 그 계약에 맞는 계획이다. 결과는 `NearestGatePlan` 의 세 값 중 하나다. 적격 집합이 비면 `ProvenEmpty` 가 되어 Lance를 실행하지 않고 빈 결과를 낸다. 순회가 있는 쿼리에 `traversal_work_limit` 이 걸려 있으면 계획기는 hop 을 비운 prefilter 를 선언해 gate 를 끈다 ([optimizer.rs L2967-L2975](https://github.com/ModernRelay/omnigraph/blob/00b8cca842f2bf009bebeefcf765672b5ff64b26/crates/omnigraph-planner/src/optimizer.rs#L2967-L2975)). gate 판정은 실행 보고에 `prefilter`, `postfilter`, `proven_empty` 로 남는다.

## 순위 보고와 exhaustive 판정

검색으로 정렬한 읽기는 JSON 응답에 `ranking` 객체를 싣는다. RFC 0047 의 "The ranking a read reports" 항목이고, 값은 계획과 그 계획을 실행한 결과로부터만 만든다.

| 필드 | 값 | 출처 |
|---|---|---|
| `by` | `nearest`, `bm25`, `rrf` | 계획의 순위 스캔 또는 `RankFuse` |
| `order` | `nearest` 는 `ascending`, 나머지는 `descending` | 순위 종류 |
| `exhaustive` | 실행이 정확했는지 | `nearest` 스캔의 `ScanReport.exact` |
| `score_columns` | 순위 점수를 그대로 담은 반환 열 | 반환 목록의 `_distance`, `_score`, `_rrf` 참조 |

### 코드 분석: `PlannedRanking::ranking`

`crates/omnigraph-planner/src/ranking.rs` [ranking.rs L41-L47](https://github.com/ModernRelay/omnigraph/blob/00b8cca842f2bf009bebeefcf765672b5ff64b26/crates/omnigraph-planner/src/ranking.rs#L41-L47)

실행 결과로 `exhaustive` 를 정하는 부분을 본다.

```rust
    pub fn ranking(self, exact: impl Fn(NodeId) -> bool) -> Ranking {
        Ranking {
            by: self.by,
            exhaustive: self.nearest_scans.iter().all(|scan| exact(*scan)),
            score_columns: self.score_columns,
        }
    }
```

`bm25` 순위는 `nearest_scans` 가 비어 있으므로 항상 `exhaustive` 다. `rrf` 는 `nearest` arm 이 정확했을 때만 `exhaustive` 다. [ranking.rs L58-L130](https://github.com/ModernRelay/omnigraph/blob/00b8cca842f2bf009bebeefcf765672b5ff64b26/crates/omnigraph-planner/src/ranking.rs#L58-L130) 의 `planned_ranking` 은 계획에서 순위 스캔 하나 또는 융합 하나만 허용하고, 그 밖의 모양은 승인 단계가 거부했어야 하는 내부 오류로 본다. `score_columns` 는 반환 목록에서 순위 binding 의 점수 열을 그대로 참조하는 항목만 고르므로, `bm25(...) > 0.0 as hit` 처럼 점수로 계산한 열은 들어가지 않는다.

실행 쪽은 [mod.rs L489-L509](https://github.com/ModernRelay/omnigraph/blob/00b8cca842f2bf009bebeefcf765672b5ff64b26/crates/omnigraph/src/engine/mod.rs#L489-L509) 의 `execute` 다. 실행이 끝난 뒤 스캔별 보고에서 `exact` 를 읽어 `ranking` 을 붙인다. 실행이 도달하지 않은 `nearest` 스캔은 보고가 없으므로 정확하지 않은 것으로 센다. "the ranking is exhaustive only on evidence" 라는 주석 그대로다.

> **주의**: RFC 0046 이 제안한 읽기 전용 `omnigraph index status` 명령(index 마다 `ready`, `unbuildable`, `missing`, `degraded` 상태 보고)은 상태가 `draft`, 구현이 `not-started` 다 ([0046-index-status.md](https://github.com/ModernRelay/omnigraph/blob/00b8cca842f2bf009bebeefcf765672b5ff64b26/docs/rfcs/0046-index-status.md)). 기준 커밋의 엔진, CLI, 서버 크레이트에서 해당 명령이나 상태 값을 찾지 못했다. 현재 index 상태를 구조화해 보는 경로는 `optimize --json` 의 `pending_indexes` 이고, 이 명령은 13장에서 다룬다.
