# 토스 AI Platform: 검토한 사용 조건을 실제 호출까지 잇는 GenAI Gateway

- **출처**: [서비스 개발에 집중할 수 있는 AI 플랫폼 만들기](https://toss.tech/article/ai-platform-foundation)
- **저자**: 원혜린, 신도현, 명세교, 김태정 (토스 AI Platform 팀)
- **발행**: 2026-10-13, 토스 기술 블로그
- **구성 요소**: GenAI Portal(신청과 설정), GenAI Gateway(LLM 호출 처리), MCP Gateway(사내 도구 실행 권한), GenAI CLI, Toss Dynamo(사내 GPU 모델 서빙), Langfuse(서비스 전체 트레이스)
- **읽은 날짜**: 2026-10-13
- **태그**: #LLMGateway #MCP #Guardrail #RateLimit #Langfuse #PTU #거버넌스 #금융규제

## 한 줄 요약

서비스 팀이 모델과 사용 목적을 정하면 거버넌스·보안·용량 검토 결과를 **프로젝트 설정**에 담는다. Gateway는 그 설정을 모든 요청에 적용한다. 핵심은 "검토한 조건"과 "실제 호출" 사이의 간극을 없애는 것이다. 수치는 공개하지 않은 설계 소개 글이다.

## 전체 구조

```
서비스 ──API 키──▶ GenAI Gateway ──▶ 외부 공급자 / Toss Dynamo(사내 GPU)
                    │ 인증 → 활성 상태 → 모델 권한 → 사용량 한도 → 입력 가드레일 → 배포 선택
                    └ 설정 조회 ◀── GenAI Portal (프로젝트: 담당자, 데이터 등급, SLA, 모델, 예산, 한도)

에이전트 ──도구 호출──▶ MCP Gateway ──▶ 사내 MCP 서버
                         └ 프로젝트 · 서버 · RPC 메서드 · 도구 이름 단위로 실행 허용 판단
```

## 1. Portal: 프로젝트를 권한과 비용의 단위로

- **모델 탐색**: 비교 항목을 골라 가격과 사양을 비교한다. 리더보드에서 가로·세로축 지표를 골라 모델별 차이를 본다. 공개 벤치마크 점수와 **사내 서빙 환경에서 잰 응답 지연**은 구분해서 보여 준다
- **프로젝트 등록**: 데이터 등급, 서비스 중단 시 영향, 담당자, 실행 환경, 모델, 예산, 사용량 제한을 등록한 뒤 API 키를 발급한다
- **키가 아닌 프로젝트 단위 관리**: 키가 여러 개여도 같은 프로젝트면 권한·예산·사용량을 합쳐서 본다. 운영 조건이 키마다 흩어지지 않게 한다
- **변경 승인**: 모델 추가나 한도 변경은 변경 전후 한도·예산과 신청 사유를 함께 보여 주고 승인을 받는다. 담당 조직은 혁신금융서비스(금융 규제 샌드박스) 허용 범위에 맞는지 확인한다
- **안내 문구**: 신청자가 가이드를 미리 읽지 않아도 되도록, 실제 사용 중 겪은 불편을 바탕으로 각 단계 안내를 다듬는다

### 데이터 등급

등급은 다루는 정보 중 **가장 민감한 항목** 기준으로 정한다.

| 등급 | 대상 |
|------|------|
| L1 | 주민등록번호, 계좌번호 등 최고 민감 정보 |
| L2 | 일반 개인정보, 개인신용정보, 행태 로그 |
| L3 | 영업비밀, 가명화한 개인정보 |
| L4 | 익명화 정보, 집계 정보 |

등급만으로 허가하지 않는다. 같은 등급이라도 목적과 환경이 다르므로 **모델과 실행 환경을 함께 검토**한다.

## 2. Gateway: 모델과 배포를 분리한다

- 요청이 오면 API 키로 프로젝트를 인증하고, 활성 상태와 모델 권한을 확인한다. 이어서 사용량 한도와 입력 가드레일을 통과한 요청만 모델로 보낸다
- **서비스가 지정하는 "모델"과 실제로 처리하는 "배포"를 구분한다.** 같은 모델이라도 공급자와 배포 환경에 따라 호출 조건이 다르다. Gateway가 혁신금융서비스 정책에 맞는 공급자 설정과 배포 상태를 보고 호출할 곳을 고른다
- 공급자별 인증과 요청 형식 변환은 **어댑터**가, 권한 확인과 사용량 제한은 **공통 로직**이 맡는다
- 사내 GPU 모델도 같은 Gateway로 호출한다. 다만 호출 형식을 맞춰도 도구 호출이나 구조화된 출력 지원 같은 **모델 기능까지 같아지지는 않는다.** 이건 서비스가 모델을 고를 때 따로 확인해야 한다

## 3. MCP Gateway: 모델 호출 권한과 도구 실행 권한을 분리

| 권한 | 판단 주체 |
|------|-----------|
| 모델 호출 | GenAI Gateway |
| 도구 실행 | MCP Gateway. 호출마다 프로젝트, 서버, RPC 메서드, 도구 이름을 확인 |
| 데이터 접근 | 도구가 연결된 서비스가 별도로 확인 |

- MCP 서버를 등록할 때 기술 보안 요건, 개인정보 처리 등급, 데이터 처리 방식을 검토한다
- 등록된 도구도 프로젝트에서 사용을 신청해야 권한을 받는다
- 저자의 예시: **"검색 도구를 실행할 수 있다고 해서 모든 문서를 읽을 수 있는 것은 아니다."**
- GenAI CLI로 터미널이나 코딩 에이전트에서 모델 목록과 등록된 MCP 도구를 조회한다

## 4. 가드레일과 로그: 본문 보호와 추적을 함께

```
요청 ─▶ 입력 검사 (프롬프트 공격, 개인정보) ─▶ 프로젝트 차단 조건에 해당하면 중단
                │
                ├─▶ 모델 호출 ─▶ 응답 검사 (지원하는 API만) ─▶ 차단 대상 응답은 반환하지 않음
                │
                └─▶ 로그 경로: 개인정보 영역 마스킹 후 전송 (설정에 따라 본문 미기록)
                     본문과 별도로 남기는 것: 호출 상태, 지연, 사용량, 실패 단계, 탐지 여부, 차단 여부
```

- 개인정보는 **규칙과 문맥 판단 모델**로 찾는다
- **"탐지"와 "차단"을 따로 기록한다.** 같은 유형을 탐지해도 프로젝트 설정에 따라 처리 결과가 다르기 때문이다
- 보안 검토용 기록은 일반 운영 로그와 목적과 경로를 나눠 관리한다
- **서비스 전체 흐름은 Langfuse 트레이스**로 본다. 서비스가 넘긴 같은 추적 식별자를 Gateway 로그에도 남겨, 트레이스를 보다가 특정 모델 호출의 상세 기록으로 넘어갈 수 있다
- Portal에서 배포 파이프라인을 고르면 Langfuse 프로젝트를 만들고 키를 파이프라인 시크릿에 등록한다. 서비스 내부 단계 계측은 서비스가 직접 한다

## 5. 예산과 처리 용량은 따로 본다

**예산이 남아 있어도 요청을 처리하지 못할 수 있다.** 그래서 예산은 누적 비용으로, 요청 수락은 분당 토큰 수(TPM) 같은 한도로 따로 관리한다.

- **예상 비용 계산**: 호출 기록에서 평균 입력·출력 토큰을 구하고, 모델 단가와 예상 요청량을 곱해 월 비용을 추정한다. 토큰 수를 임의로 가정하지 않는다
- **예산 초과 처리**: 일정 비율 도달 시 알림. 초과 후에는 알림, 유예 기간, 프로젝트 비활성화 조건을 나눠 둔다

### SLA 등급

| 등급 | 대상 |
|------|------|
| High | 전용 파이프라인에서 가용성, 응답 시간, 처리량 보장이 필요한 서비스 |
| Standard | 공유 모델에서 필요한 최소 처리량을 확보하는 서비스 |
| Flex | 처리량을 보장하지 않는 실험이나 지연 허용 작업 |

데이터 등급은 민감도를, SLA 등급은 운영 수준을 정한다. High와 Standard는 플랫폼팀의 용량 검토를 거친다. 모델 전체 한도에 걸리면 **우선순위가 낮은 요청부터** 제한한다.

## 6. 끝나지 않은 요청도 사용량에 넣는다

LLM 호출은 응답이 끝나야 최종 토큰 수를 안다. 완료된 요청만 세면 처리 중인 요청이 빠져, 여유가 없는데도 새 요청을 계속 받게 된다.

| 시점 | 처리 |
|------|------|
| 요청 수락 | 입력과 예상 출력 토큰을 **먼저 예약** |
| 응답 완료 | 실제 사용량으로 보정 |
| 스트리밍인데 최종 사용량을 못 받음 | 추정치 사용 |
| 캐시에서 반환해 모델을 호출하지 않음 | 예약분 차감 |
| 응답이 늦게 끝남 | **처음 예약한 시점의 값**을 고친다. 완료 시점에서 빼면 엉뚱한 시간대의 한도가 늘어난다 |

이 계산은 한도 관리용이며 비용 청구와는 별개다. 스트리밍, 실패, 재시도에서도 맞도록 Gateway가 관리한다.

## 7. 약정 용량(PTU) 우선, 부족하면 종량제(PAYG)

- PTU(Provisioned Throughput Unit, 미리 확보하는 처리 용량 단위) 우선 라우팅이 설정된 모델은 확보한 용량부터 쓰다가, 처리하기 어려워지면 **같은 모델**의 PAYG 경로로 전환한다
- 어려운 부분은 전환 뒤의 동작이다
  - 일시 제한이 풀렸는데도 PTU를 계속 빼 두면 확보한 용량을 놀리면서 PAYG 비용이 나간다
  - 장애 난 배포에 계속 보내면 실패와 지연이 는다
- Gateway는 오류 유형에 따라 그 배포로의 요청을 잠시 중단하거나 재시도 간격을 늘린다. 다른 경로를 쓰는 동안에도 기존 배포의 복구를 확인하고, 복구되면 PTU로 돌아간다
- **바뀌는 것은 호출 경로이지 모델이 아니다.** 모델 전환은 품질이 달라지므로 별도 평가 후 서비스 담당자가 판단한다

## 8. 역할 분담과 다음 글

거버넌스·보안 담당은 사용 조건을, 모델·서빙 담당은 처리 용량을 검토한다. AI Platform 팀은 그 결과가 프로젝트 설정과 요청 처리에 반영되도록 잇는다. 모델 적합성과 결과 품질은 여전히 서비스 팀과 함께 풀 문제로 남긴다. 다음 글은 토스 서비스에 맞는 평가 기준과 그 결과를 모델 선택·운영 최적화에 쓰는 과정이다.

## 읽을 때 감안할 것

- **정량 지표가 하나도 없다.** 연동 서비스 수, 호출량, Gateway가 더하는 지연, 가드레일의 탐지율과 오탐률, PTU 활용률 같은 수치가 없어 설계의 효과를 판단할 수 없다.
- **가드레일의 방식이 거의 드러나지 않는다.** 프롬프트 공격 탐지를 어떤 방식으로 하는지(분류기, 규칙, LLM 판정)와 지연 비용을 밝히지 않는다. 개인정보는 "규칙과 문맥 판단 모델"이라고만 한다.
- **응답 검사는 지원하는 API에서만 한다.** 어떤 API가 빠지는지, 스트리밍 응답은 어떻게 검사하는지 적혀 있지 않다.
- **금융 규제 환경이 전제다.** 혁신금융서비스 승인 절차와 데이터 등급 L1~L4는 토스 내부 기준이라, 규제가 약한 조직에서는 같은 무게의 승인 단계가 과할 수 있다.
- **토큰 예약에서 "예상 출력" 추정 방법을 밝히지 않는다.** max_tokens를 그대로 쓰는지 과거 평균을 쓰는지에 따라, 한도를 과하게 예약하거나 덜 예약할 수 있다.

## 가져갈 지점

- **"모델"과 "배포"를 나눈다.** 서비스는 모델 이름만 지정하고, 공급자·리전·약정 용량 선택은 Gateway가 정책과 상태로 결정한다. PTU와 PAYG 전환, 장애 우회가 서비스 코드 변경 없이 가능해진다.
- **권한을 세 층으로 나눈다.** 모델 호출, 도구 실행, 데이터 접근을 각각 다른 주체가 판단한다. MCP 도구를 붙일 때 "도구를 쓸 수 있음"과 "그 데이터를 볼 수 있음"을 섞지 않는 기준으로 바로 쓸 수 있다.
- **탐지와 차단을 따로 기록한다.** 가드레일 정책을 조정할 때 "얼마나 탐지했는데 설정 때문에 통과시켰는가"를 알 수 있어야 임계값을 근거로 바꿀 수 있다. [가드레일 읽을 논문](../_maps/guardrail_%EC%9D%BD%EC%9D%84_%EB%85%BC%EB%AC%B8.md)의 탐지 방법을 실제로 운영할 때 필요한 기록 구조다.
- **진행 중 요청은 예약으로 세고, 예약 시점의 값을 보정한다.** LLM 레이트 리미터를 직접 만들 때 놓치기 쉬운 부분이다.
- **트레이스와 Gateway 로그를 같은 ID로 잇는다.** 서비스 단 트레이스(Langfuse)와 Gateway 단 상세 로그를 추적 ID 하나로 오갈 수 있게 한다. Langfuse 자체의 구조는 [Opik과 Langfuse 비교](../repos/%5B20230510%5D%20comet-ml_opik_LLM관측평가_플랫폼_Langfuse비교.md)에 정리했다.

## 결론

LLM Gateway 설계에서 무엇을 공통으로 맡겨야 하는지 보여 주는 체크리스트로 쓰기 좋은 글이다. 프로젝트 단위 권한, 모델과 배포 분리, 3층 권한, 탐지와 차단 분리 기록, 토큰 예약, PTU 복귀가 그 목록이다. 수치가 없으므로 설계 근거가 아니라 설계 항목 목록으로 인용한다.
