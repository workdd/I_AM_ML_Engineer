## 한 줄 요약

비용이 오르는데 원인을 모르던 상태에서 **API별 토큰 메트릭을 먼저 만들었더니** 속성 추출 API 하나가 토큰의 대부분을 쓰고 있었다. 이 API는 매 호출마다 같은 15K 시스템 프롬프트를 다시 보내고 있었다. 프롬프트의 고정부와 변동부를 분리하고 Bedrock 캐시 포인트(TTL 1시간)를 붙여 전체 LLM 청구액을 64% 줄였다.

## 1. 문제: 비용은 보이는데 원인이 안 보인다

Bedrock 콘솔은 일별 입력·출력 토큰과 비용 합계만 보여 준다. 아래 질문에 답할 수 없었다.

- 토큰을 가장 많이 쓰는 API
- 입력, 출력, 캐시 읽기, 캐시 쓰기의 비중
- 시간대별 분포와 호출량

저자의 결론은 **"첫 번째 문제는 비용이 아니라 가시성"** 이다.

## 2. API별 토큰 메트릭 파이프라인

LangChain4j의 `ChatModelListener`로 구현했다. 세 조각으로 나뉜다.

| 조각 | 방법 | 설계 포인트 |
|------|------|-------------|
| 요청 경로 태깅 | 서블릿 필터가 요청 경로를 `ThreadLocal`에 저장 | Prometheus 카디널리티 폭발을 막으려고 allowlist 경로만 태그로 남기고 나머지는 `other` |
| 메트릭 기록 | 매 Bedrock 호출 종료 시 토큰 수, 요청 수, 지연, 에러를 기록 | 태그: `llm_endpoint`, `llm_model`, `type`(input / output / cache_read / cache_write) |
| 비용 계산 | 코드에서 빼고 Grafana 변수(토큰 단가)로 계산 | 단가가 바뀌어도 재배포 없이 대시보드 변수만 수정 |

```kotlin
class MetricsChatModelListener(private val registry: MeterRegistry) : ChatModelListener {
    override fun onResponse(ctx: ChatModelResponseContext) {
        val endpoint = LlmEndpointContext.current() ?: "other"   // 서블릿 필터가 채워 둔 값
        val model = ctx.chatResponse().metadata().modelName()
        val usage = ctx.chatResponse().metadata().tokenUsage()
        fun recordTokens(type: String, count: Int) =
            registry.counter("llm_tokens_total",
                "llm_endpoint", endpoint, "llm_model", model, "type", type,
            ).increment(count.toDouble())
        recordTokens("input", usage.inputTokenCount())
        recordTokens("output", usage.outputTokenCount())
        // cache_read / cache_write 도 같은 방식
    }
}
```

## 3. 원인: 한 API가 토큰의 대부분

`/extraction/attributes`(속성 추출) 하나가 토큰의 대부분을 썼다. 나머지 endpoint(컬러 추출, 그룹 평가, Slack 이벤트 등)는 합쳐도 노이즈 수준이었다. 비율 수치는 본문과 그림이 다르다 (아래 "읽을 때 감안할 것").

## 4. 본질: 같은 15K 프롬프트를 매번 다시 보냄

```
요청 = [시스템 프롬프트 약 15K 토큰] + [상품 최대 100개, 약 2K 토큰] = 약 17K
총 토큰 = 15K × N (매번 동일) + 2K × N (호출마다 변동)
```

시스템 프롬프트에는 추출 규칙, 예시, 금지 항목, 출력 JSON 스키마가 들어 있다. 변동부의 7~8배 크기다. 토큰을 많이 쓴 이유는 프롬프트가 유난히 커서가 아니라 **같은 prefix를 반복하는 고빈도 호출**이었기 때문이다.

## 5. 옵션 결정: LLM으로 시뮬레이션, 계산은 결정론적으로

| 옵션 | 절감 효과 | 구현 공수 | 정확도 영향 |
|------|-----------|-----------|-------------|
| **Prompt Caching (채택)** | 시스템 프롬프트 부분 약 90% | 낮음 | 없음 |
| 모델 다운사이즈 (상위에서 하위 모델로) | 단가 약 67% 인하 | 중간, 정확도 검증 필요 | 잠재적 영향 |
| Batch API 전환 | 일반가 대비 50% 추가 할인 | 큼, polling 구조 재설계 | 없음 |

옵션 순서는 LLM 기반 비용 시뮬레이션으로 정했다.

- **입력**: 코드베이스에서 뽑은 호출 패턴(어떤 endpoint가 어떤 프롬프트로 얼마나 자주 부르는지), 모델별 단가(input / output / cache_read / cache_write), 메트릭으로 모은 실제 일일 토큰 분포
- **출력**: 옵션별 예상 절감률, 적용 우선순위, 옵션 간 의존성 (예: 캐싱이 먼저 들어가야 Batch API의 ROI를 다시 계산할 수 있음)
- **역할 분리**: LLM에는 호출 패턴 추출과 시나리오 구성까지만 맡겼다. 최종 금액은 Grafana의 실측 토큰량에 단가를 곱해 내고 Bedrock 콘솔 수치와 대조했다. 저자는 "LLM에 산술까지 맡기면 그럴듯한 숫자를 지어낼 수 있다"고 쓴다.

## 6. 적용

### 6.1 사전 작업: 고정부와 변동부 분리

Prompt Caching은 prefix 매칭이라 앞에서부터 일치하는 구간까지만 재사용한다.

| 구분 | 위치 | 예 |
|------|------|-----|
| 고정값 | 시스템 프롬프트 (캐시 영역) | 규칙, 지시문, 예시, 스키마 |
| 변동값 | 유저 메시지 (캐시 밖) | 상품명, 카테고리 ID, 사용자 입력 |

기존 코드는 이 구분이 흐려져 있어서 분리 작업을 먼저 했다. 저자는 "캐시 포인트 한 줄 추가로 끝나는 일이 아니다"라고 강조한다.

### 6.2 Bedrock 캐시 포인트

```kotlin
val cachePoint = SystemContentBlock.builder()
    .cachePoint(
        CachePointBlock.builder()
            .type(CachePointType.DEFAULT)
            .ttl(CacheTTL.VALUE_1_H)       // 1시간 TTL
            .build()
    ).build()
val system = systemPromptBlocks + cachePoint
```

- 마커를 만나면 Bedrock이 시스템 블록까지의 K, V를 캐시에 저장하고, 같은 prefix 요청에서 메모리로 읽는다
- TTL은 **히트할 때마다 1시간으로 갱신**된다. 1시간 동안 히트가 한 번도 없어야 만료된다 (AWS 문서 기준이라고 저자가 명시)
- 캐시는 자사 AWS 계정 안에서만 재사용되고, 시스템 프롬프트에 민감정보가 없어 노출 우려가 없다고 판단했다
- 작업 당시 LangChain4j Bedrock 모듈은 TTL 없이 캐시 포인트를 만들어 5분 기본값만 가능했다. 그래서 SDK를 직접 호출해 우회했고, `BedrockChatRequestParameters`에 `cacheTtl`을 추가하는 PR #4920을 기여했다 (main 머지, 릴리스 대기)

## 7. 결과

| 지표 | 적용 전 | 적용 후 (1주 측정) |
|------|---------|--------------------|
| cache_read 토큰 비중 | 0% | 약 98% |
| cache_write 토큰 비중 | 0% | 약 1.5% (캐시 첫 적재) |
| 일일 비용 | 100% | **64% 절감** |
| 정확도 | | 동일 |
| 코드 변경량 | | 핵심 3줄 (프롬프트 분리 작업은 별도) |

- 본문은 64%를 **특정 API가 아닌 전체 LLM 청구액 기준**이라고 밝힌다
- 시뮬레이션 예측 절감률 약 63%, 실측 약 64%로 1%p 차이가 났다. 저자는 이 결과를 근거로 다음 단계 시뮬레이션도 같은 신뢰도로 쓸 수 있다고 본다

## 8. Prompt Caching 활용 패턴 6가지

| # | 패턴 | 내용 |
|---|------|------|
| 1 | 시스템 프롬프트 캐싱 | 고정 규칙·예시를 시스템 블록에 두고 캐시 (이 글이 적용한 방식) |
| 2 | Tool 정의 캐싱 | 툴·함수 스펙을 앞단에 고정 배치 |
| 3 | 대화 히스토리 캐싱 | 멀티턴 누적 대화의 재처리 방지 |
| 4 | RAG 문서 캐싱 | 긴 참조 문서를 반복 질의에 재사용 |
| 5 | Cache Warming | 병렬 발사 전 워밍 콜 1회로 선적재. Thomson Reuters Labs는 한 자릿수 히트율이 80%대로 올랐다고 보고 |
| 6 | Relocation Trick | 시스템 프롬프트 속 동적 값(타임스탬프, 요청 ID, 사용자 ID)을 유저 메시지로 이동. ProjectDiscovery는 한 자릿수에서 70%대로 상승 |

5와 6은 외부 사례의 수치이며 이 글이 직접 잰 것이 아니다.

## 9. 캐시를 깨뜨리는 안티패턴

캐시가 안 맞아도 **API는 에러를 내지 않고 `cache_read`가 0으로 찍힐 뿐**이다. 메트릭을 보지 않으면 모르고 지나간다.

| 안티패턴 | 증상 | 해결 |
|----------|------|------|
| 시스템 프롬프트에 타임스탬프 | 매초 해시가 바뀜 | 동적 값을 유저 메시지로 |
| 시스템 프롬프트에 사용자 ID | 사용자마다 다른 해시 | 플레이스홀더 |
| JSON 키 순서 비일관 | 직렬화 결과가 매번 다름 | 키 정렬 강제 |
| 병렬 요청 동시 발사 | 첫 cache write가 끝나기 전 나머지가 모두 miss | 워밍 콜 1회 선행 |
| Tool 정의 순서 변경 | 전체 캐시 무효화 | 알파벳순 고정 |
| 최소 토큰 미달 | 에러 없이 캐시되지 않음 | 모델별 최소 토큰 확인 |

원칙은 하나다. **변경 빈도가 낮은 것을 앞에, 높은 것을 뒤에 둔다.** 앞이 바뀌면 뒤는 전부 무효화된다.

## 읽을 때 감안할 것

- **속성 추출 API의 비중 수치가 본문과 그림에서 다르다.** 본문은 "전체 LLM 토큰의 약 92%"이고, 그림 3은 "endpoint별 일일 입력 토큰 비중 99.9%"다. 분모가 전체 토큰인지 입력 토큰인지에 따라 달라질 수 있지만 글에서 설명하지 않는다.
- **64%의 기준이 본문과 그래프 캡션에서 다르다.** 본문은 "전체 LLM 청구액 기준"이고, 일일 비용 시계열(그래프 1) 캡션은 "해당 API 기준, 상대값"이다.
- **그래프 1의 라벨과 점이 맞지 않는다.** 적용 후 라벨은 "평균 36, 약 64% 감소"인데, 그려진 점은 y축 약 43~45에 놓여 있다. 점 기준으로 읽으면 감소폭은 55% 안팎이다. 그래프가 실측이 아니라 설명용으로 그린 것일 수 있다.
- **"캐시 히트율 98%"와 "cache_read 토큰 비중 98%"가 섞여 쓰인다.** 호출마다 캐시 밖 변동부 약 2K가 있으므로, cache_read가 입력 토큰 전체의 98%가 되기는 어렵다 (15K/17K ≈ 88%). 분모가 cache_read + cache_write로 보인다. 이 부분은 글에 나온 수치로 따져 본 추론이다.
- **시뮬레이션과 실측의 1%p 일치를 일반화하기 어렵다.** 고정 prefix가 입력의 대부분인 단일 배치 워크로드라 캐싱 효과를 예측하기 가장 쉬운 경우다. 정확도 변화가 걸린 모델 다운사이즈에 "같은 신뢰도"를 적용할 근거는 되지 않는다.
- **적용 전후 1주씩 비교라 호출량 변화를 통제하지 않았다.** 사용 모델명과 절대 비용도 밝히지 않아 다른 환경에 그대로 옮길 수 없다.

## 가져갈 지점

- **비용 최적화의 첫 작업은 분해 가능한 메트릭이다.** endpoint, 모델, 토큰 종류(input / output / cache_read / cache_write)로 쪼개 보지 않으면 원인도 효과도 판단할 수 없다. 단가를 코드가 아닌 대시보드 변수로 두는 것도 바로 쓸 수 있는 설계다.
- **cache_read를 상시 모니터링 대상으로 둔다.** 캐시 실패는 조용히 일어난다. 타임스탬프 한 줄, JSON 키 순서, 툴 정의 순서만 바뀌어도 캐시가 깨진다. 에이전트 시스템 프롬프트에 날짜나 사용자 정보를 넣는 경우가 많아 특히 주의해야 한다.
- **프롬프트는 변경 빈도 순서로 쌓는다.** 툴 정의, 시스템 규칙, 참조 문서, 대화 히스토리, 사용자 입력 순서다. 캐싱을 쓰지 않더라도 프롬프트 구조를 정리하는 기준이 된다.
- **LLM에는 판단을, 산술은 코드에 맡긴다.** 호출 패턴 추출과 시나리오 구성은 LLM이 하고, 금액 계산은 실측 토큰과 단가로 결정론적으로 한다.
- **병렬 배치는 워밍 콜을 먼저 보낸다.** 동시에 보내면 첫 write가 끝나기 전 요청이 모두 miss가 된다.
- 토큰을 줄이는 다른 접근은 [JSON vs TOON 토큰효율](%5B20260104%5D%20네이버클라우드_JSON_vs_TOON_토큰효율.md)에 있다. 그쪽은 입력 표현을 줄이고, 이 글은 같은 입력의 재계산을 줄인다.

## 결론

Prompt Caching 적용기라기보다 **"가시성부터 확보하는 비용 최적화 절차"** 로 읽는 것이 맞다. 메트릭 설계, 고정부와 변동부 분리, 안티패턴 표는 그대로 가져다 쓸 수 있다. 반면 64%, 98% 같은 헤드라인 수치는 본문과 그림 사이에 기준이 엇갈려 다른 곳에 근거로 인용하기 어렵다.
