## 한 줄 요약

작은 치과가 **환자 정보를 병원 밖으로 내보내지 않는다**는 원칙 하나로, 뒷방에 DGX Spark 12대와 Mac mini를 두고 전화 응대, 보험 서류 대조, 사내 검색, 경영 리포트를 자동화한 경험담이다. 코드는 거의 AI 코딩 에이전트(Claude Code, Codex)가 썼다. 수치는 모두 글쓴이의 주장이고 검증 방법은 공개하지 않았다.

## 인프라

| 장비 | 역할 |
|---|---|
| NVIDIA DGX Spark급 12대 | 4대씩 묶어 큰 모델 하나를 돌린다. DeepSeek 4대, GLM 4대, 나머지 실험용 |
| Mac mini M5 Pro 64GB 2대 + M4 1대 | 음성(STT, TTS), 검색, 서류 판독. 같은 구성 두 대로 한 대가 죽어도 멈추지 않게 함. M4는 에이전트 브라우저로 크론 작업과 보험 청구 사이트 작업 |
| 가상화 서버 3대 | 사내 포털, 치과 관리 프로그램, 전화 교환기(PBX), 백업, 감시 |
| UPS 6대 | 정전 시 장비끼리 신호를 주고받으며 순서대로 종료하고, 복전되면 다시 켬 |

**DGX Spark를 고른 이유** (2편 "과투자" 해명 부분):
- **메모리.** 큰 모델은 수백 GB가 필요하다. RTX PRO 6000은 96GB, H200은 141GB인데, DGX Spark는 한 대 128GB이고 4대를 묶으면 512GB다. 느려도 큰 모델이 통째로 올라간다.
- **전기, 열, 소음.** 일반 콘센트로 돌아가고 전기 공사가 필요 없다.
- **커뮤니티.** NVIDIA 포럼에 "최신 모델을 스파크 4대로 돌리는 설정"이 계속 올라와, 비전공자도 따라 할 수 있다.
- **속도보다 정확도.** 보험 서류나 경영 숫자는 "1초 빨리 틀리는 것보다 3초 늦어도 맞는 게" 중요하다고 봤다.
- Mac Studio 512GB도 검토했지만 MLX 생태계가 맞지 않는다고 판단해 제외했다.

운영 팁 하나: 고속 연결 케이블을 전원이 켜진 채로 꽂으면 속도가 10분의 1로 굳고, 재부팅으로도 안 풀린다. 플러그를 뽑고 1분 기다려야 풀린다.

| 상담·동의서 | 상담 내용 STT 전사, 태블릿 전자 동의서(설명 그림 포함), 서명 즉시 PDF로 차트 저장 | 종이 동의서 제거 |

| 근태 | 출입문 NFC 태그로 출퇴근 기록 → 근무 시간과 시급 자동 계산 | 종이 출근부 제거 |
| 마케팅 | 광고 대행 해지. 홈페이지를 환자가 실제로 검색하는 말로 정리(SEO), 생성형 AI가 추천하기 좋게 구조화(GEO) | 마케팅비 0원. "ChatGPT·Gemini 추천으로 왔다"는 환자 증가 |

비용 면에서는 전화 시스템 계약 해지로 450만 원을 아꼈고, 전화 녹음·요약, OCR, 예약 문자, 각종 AI 구독을 원내 서버로 바꿔 해지했다고 한다.

## 운영 원칙

- **환자 정보는 병원 밖으로 나가지 않는다.** 장비 비용이 들어도 이 원칙은 버리지 않는다. 클라우드 AI를 쓰지 않는 이유다.
- **숫자는 AI가 계산하지 않는다.** 분석 프로그램이 계산한 값만 쓰고, AI는 그 숫자를 해석해 글로 푼다. 추정한 내용은 `[추정]`으로 따로 표시하게 한다.
- **AI는 원장 기록에 직접 쓰지 않는다.** 치과 관리 프로그램에는 읽고 정리하고 제안하는 데까지만 한다. 판단은 사람이 한다.
- **모델 두 개로 교차 검증한다.** 같은 일을 DeepSeek와 GLM에 시키고, 답이 다르면 사람이 본다. 월간 진단은 세 모델이 같은 말을 하면 진짜 문제로 보고, 의견이 갈리면 원장이 들여다본다.

## 사람 평가 화면

통화 요약 분류(목적, 상대, 급함, 할 일, 예약, 가격 문의, 불만, 응급·통증)가 맞는지 원장이 직접 채점하는 화면을 만들었다.

- **숫자키만으로 채점한다.** 한 건에 몇 초면 끝난다.
- **"모델 엇갈림" 건부터 본다.** DeepSeek와 GLM의 판정이 다른 통화가 우선이다.
- **블라인드 비교 탭.** 어느 모델이 쓴 답인지 가리고 "1이 나음 / 2가 나음 / 비슷 / 둘 다 틀림"을 고른다.
- 모인 판정은 **정답 데이터**가 된다. 어느 모델이 우리 병원 전화를 더 잘 알아듣는지 숫자로 비교하고, 나중에 병원 맞춤 학습 재료로 쓴다.

## AI 코딩 에이전트 운영

- 역할별 에이전트를 여러 개 띄운다: 포털, 전화 시스템, 음성 서버, 인프라. 에이전트끼리 메시지를 주고받으며 일한다("이 서버 재시작할 건데 괜찮음?" "잠깐, 지금 녹음 시험 중").
- **운영 중인 설정 변경은 원장이 직접 승인해야 한다.** 에이전트끼리 "원장님이 된대"라고 전해 들은 승인은 인정하지 않는다.
- 에이전트끼리 크로스체크한다. 설정 누락으로 방송 이름 변환이 6초씩 걸린 것을 다른 에이전트가 운영 전에 잡았고, 시험 수치를 잘못 적은 것도 다른 에이전트가 지적해 고쳤다.
- 재무 CLI는 처음 받는 질문이면 처리 방법을 스킬로 만들어 두고, 같은 질문이 오면 그 스킬을 꺼내 쓴다.

## 읽을 때 감안할 것

- **수치는 전부 자기 보고다.** 77% 자동 확정, 28개 중 26개 같은 수치의 판정 기준과 표본 구성은 공개하지 않았다. "실패 0쪽"도 판독이 끝났다는 뜻인지 정확했다는 뜻인지 불분명하다.
- **규모가 일반적이지 않다.** DGX Spark 12대는 동네 치과 기준으로 큰 투자이고, 글쓴이도 "취미에 미쳐서 과투자한 것에 가깝다"고 한다. 그대로 따라 할 사례라기보다 설계 원칙을 볼 사례다.
- **본문도 AI로 썼다고 밝힌다.** 문맥이 맞지 않는 부분이 있을 수 있다고 직접 적었다.
- **환자 정보를 다루는 규제 측면**(의료법상 전자의무기록, 녹음 고지 등)은 글에서 다루지 않는다.
- 글쓴이가 밝힌 병목은 기술보다 사람과 디지털 전환이다. 고령 환자는 여전히 종이 차트가 필요하다.

## 가져올 수 있는 부분

| 대상 | 가져올 수 있는 부분 |
|---|---|
| LLM 리포트·답변 | **숫자는 프로그램이 계산하고 LLM은 해석만 한다**, 추정은 `[추정]`으로 표시한다. 문서 작성 규칙의 "수치는 원자료에서"와 같은 원칙을 시스템에 박아 넣은 형태다 |
| 대조 업무 자동화 | 결과를 "확정 / 확인 필요"로 나눠 사람은 확인 필요만 보게 하는 구성. 자동화 비율(77%)이 곧 성과 지표가 된다 |
| 평가 데이터 수집 | 숫자키 채점 화면, 모델 판정이 엇갈린 건부터 보기, 출처를 가린 블라인드 쌍 비교. 이렇게 모인 판정을 정답 데이터와 모델 선정 근거로 쓴다 |
| 교차 검증 | 서로 다른 모델 두세 개에 같은 일을 시키고 불일치만 사람에게 올리는 방식. 사람 검토량을 줄이면서 오류를 잡는다 |
| 모델 선정 | 후보 모델을 **실제 업무 문서**(흐린 스캔본)로 비교하고, 업무 핵심 필드(금액) 정답률로 고른다 |
| 에이전트 권한 | 운영 설정 변경은 사람의 직접 승인만 인정하고, 에이전트 사이에서 전달된 승인은 무효로 하는 규칙 |
| 검색 품질 확인 | 실제 사용자 질문으로 작은 평가 세트(28개)를 만들어 정답 수를 세는 방식 |
