## 한 줄 요약

LLM이 사내 데이터로 답할 때 **관계를 여러 단계 따라가거나 관계의 규칙(전이, 역관계)이 중요한 질문**에는 벡터 검색이나 Text-to-SQL이 아니라 지식 그래프가 필요하고, 그 관계의 뜻과 규칙을 정의한 설계도가 온톨로지라는 입문 글이다. 가상 금융그룹("도토리금융그룹") 예제로 설명한다.

## 질문 유형별 도구

| 데이터와 질문 | 주로 쓰는 도구 | 예 |
|---|---|---|
| 비정형 문서에서 비슷한 내용 찾기 | 벡터 검색 | "이 펀드의 환매 수수료 규정은?" |
| 정형 테이블 조회·필터·집계 | Text-to-SQL (Genie 등) | "지난달 판매액 상위 5개 상품은?" |
| 테이블 사이 관계를 여러 단계 따라가거나 관계 규칙이 중요한 질문 | 지식 그래프 (의미는 온톨로지로 정의) | "도토리홀딩스가 직·간접적으로 지배하는 회사가 판매하는 1등급 상품은?" |

세 번째 질문에 답하려면 테이블에 적혀 있지 않은 세 가지를 알아야 한다.
1. **관계의 뜻**: `control` 테이블의 한 줄(홀딩스 → 증권)은 "지배한다"는 뜻이다
2. **관계를 이어 가는 규칙**: 홀딩스가 증권을, 증권이 자산운용을 지배하면 홀딩스는 자산운용도 지배한다 ("직·간접")
3. **반대 방향**: "증권은 누구의 지배를 받나?"는 같은 관계를 거꾸로 읽은 질문이다

이 의미를 한 번 정의해 두고 프로그램이 그대로 쓰게 하는 것이 온톨로지다.

## 시맨틱 레이어, 온톨로지, 지식 그래프

```
시맨틱 레이어 (업무 의미 전체: 용어, 지표, 관계)
 └─ 온톨로지 (개념, 관계, 규칙의 설계도. 표준 형식은 OWL)
      └─ 지식 그래프 (설계도에 실제 데이터를 채운 것)
```

| 개념 | 정의 | 예 |
|---|---|---|
| 시맨틱 레이어 | 원천 데이터와 그것을 쓰는 도구 사이에서 기술 구조를 업무 용어·지표·관계로 정의한 층. 어떤 도구로 조회하든 같은 뜻으로 쓰인다 | "계열사 = 도토리홀딩스가 직·간접 지배하는 회사" |
| 온톨로지 | 그중 개념(클래스), 관계, 규칙을 표준 형식(OWL)으로 정의한 것. 무엇이 있을 수 있는지 정하는 설계도 | "controls는 회사 → 회사 관계이고 전이된다" |
| 지식 그래프 | 온톨로지에 실제 데이터를 채운 것 | "도토리홀딩스 controls 도토리증권" |

Databricks에서의 역할 분담:

| 층 | 기능 | 역할 |
|---|---|---|
| 지표 정의 | UC Metric Views (GA) | 지표와 차원을 한 번 정의해 대시보드와 Genie가 같이 씀 |
| 자연어 질의 맥락 | Genie Ontology (Public Preview) | 테이블·쿼리·대시보드에서 업무 맥락을 자동으로 모음. 이름과 달리 형식 온톨로지(OWL)가 아니다 |
| 형식 온톨로지 + 지식 그래프 | OntoBricks (Databricks Labs) | 클래스·관계·규칙을 OWL로 정의하고 테이블을 그래프로 만들어 추론·검증·질의 |

OntoBricks는 Databricks 공식 제품이 아니다. 공식 지원(SLA) 대상이 아니고 GitHub 이슈로만 대응하며 버전이 빠르게 바뀐다.

## 지식 그래프: 트리플

사실을 **주어 - 관계 - 대상** 세 조각(트리플)으로 저장한다.

| 주어 | 관계 | 대상 |
|---|---|---|
| 도토리홀딩스 | controls | 도토리증권 |
| 도토리증권 | controls | 도토리자산운용 |
| 도토리자산운용 | sells | 도토리글로벌테크펀드 |
| 도토리글로벌테크펀드 | riskGrade | 1 (값) |
| 전유성 | executiveOf | 도토리증권 |

앞의 질문은 "도토리홀딩스에서 controls를 한 번 이상 따라간 뒤 sells를 따라가 riskGrade = 1인 노드 찾기"라는 경로 탐색이 된다. 하지만 트리플에는 사실만 있고, "controls를 두 번 따라간 것도 지배인가", "controls의 주어로 사람이 올 수 있나" 같은 **사실에 대한 규칙**은 없다. 이것을 적는 곳이 온톨로지다.

## 온톨로지의 구성

| 구성 요소 | OWL 용어 | 뜻 | 예 |
|---|---|---|---|
| 클래스 | Class | 엔티티의 종류 | Company, Person, Product |
| 개체 | Individual | 클래스에 속한 하나. `rdf:type`으로 연결 | 도토리증권 `rdf:type` Company |
| 객체 속성 | Object Property | 엔티티와 엔티티 사이 관계. domain(주어 쪽)과 range(대상 쪽) 지정 | executiveOf: Person → Company |
| 데이터 속성 | Datatype Property | 엔티티와 값 사이 관계 | riskGrade |
| 상하위 관계 | `rdfs:subClassOf` | 클래스 사이 "~의 일종" | FinancialCompany ⊂ Company |

- **DB 스키마와의 차이**: 스키마는 데이터를 담는 틀이고, 온톨로지는 거기에 **새 사실을 이끌어 내는 규칙**까지 담는다 (지배의 지배는 지배 → 간접 지배).
- **domain/range는 검사가 아니라 추론 규칙이다.** RDB 제약처럼 틀린 데이터를 막는 게 아니라, 타입이 비어 있는 개체의 타입을 채운다.
- **TBox와 ABox**: TBox는 개념 정의(스키마, 설계도), ABox는 개별 사실(데이터). 시리즈의 핵심 기준이고, OntoBricks에서는 **LLM이 TBox 설계를 돕고 ABox는 테이블에서 SQL로 만든다.**

Turtle(`.ttl`) 파일 예:

```turtle
fin:Company        a owl:Class .
fin:controls       a owl:TransitiveProperty .          # 전이 관계
fin:controls       rdfs:domain fin:Company .           # 주어는 회사
fin:isControlledBy owl:inverseOf fin:controls .        # 반대 방향
fin:DotoriHoldings fin:controls fin:DotoriSecurities .  # 사실 (ABox)
```

## 읽을 때 감안할 것

- **입문 1편이라 OntoBricks 자체는 거의 나오지 않는다.** 설계 → 매핑 → 추론·검증 → 에이전트 제공(Design, Map, Reason, Serve) 흐름과 LLM이 맡는 범위는 2편에서 다룬다.
- **추론 비용과 한계는 다루지 않는다.** OWL 추론은 표현력에 따라 계산 비용이 크게 달라지는데, 어떤 OWL 수준을 쓰는지는 이 글에 없다.
- **RDF/OWL 계열 설명이다.** 노드·엣지에 속성을 붙이는 속성 그래프(Apache AGE, Neo4j 등)와는 모델이 다르다. 전이·역관계를 속성 그래프에서는 질의(가변 길이 경로)로 풀어야 한다.
- OntoBricks는 Databricks Labs 실험 프로젝트라 운영 도입 전 지원 범위를 따로 확인해야 한다.

## 가져올 수 있는 부분

| 대상 | 가져올 수 있는 부분 |
|---|---|
| 질의 라우팅 | 질문을 "비슷한 내용 찾기 → 벡터 / 조회·집계 → SQL / 관계 여러 단계·관계 규칙 → 그래프"로 나누는 기준. GraphRAG를 언제 쓸지 설명할 때 그대로 쓸 수 있는 표다 |
| 그래프 스키마 설계 | 관계마다 **전이 여부, 역관계, domain/range**를 명시하는 습관. 소속·상위 개념 트리를 깊이·경로 속성으로 미리 풀어 두는 설계는 사실상 전이 관계를 속성으로 펼친 것이라, 어떤 관계가 전이인지 문서로 적어 두면 질의 작성과 검증 기준이 명확해진다 |
| TBox / ABox 분리 | 스키마(관계 정의)는 사람과 LLM이 설계하고, 사실(데이터)은 원천 테이블에서 SQL로 결정적으로 만든다는 역할 분담. LLM이 사실을 생성하지 않게 하는 경계다 |
| 용어 정리 | 시맨틱 레이어 ⊃ 온톨로지 ⊃ 지식 그래프 관계와 "Genie Ontology는 형식 온톨로지가 아니다" 같은 구분. 문서나 설명에서 용어를 섞어 쓰지 않는 데 쓸 수 있다 |
| 예제 구성 | 가상 회사 데이터로 다단계 지배 질문 하나를 끝까지 따라가는 설명 방식. 그래프 질의를 처음 보는 사람에게 보여 줄 때 참고할 만하다 |
