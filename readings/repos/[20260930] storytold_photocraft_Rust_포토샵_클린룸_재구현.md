- **태그**: #Rust #ImageEditor #PSD #MCP #CommandRegistry #AgentReady #CleanRoom

## 한 줄 요약

포토샵의 메뉴, 단축키, 도구, PSD 파일을 공개 명세와 관찰한 동작만으로 다시 만든(클린룸) 이미지 편집기다. 편집기 자체보다 눈여겨볼 것은 **모든 기능을 명령 하나의 등록부(500개 이상)에 올리고, 화면·CLI·JSON 제어 채널·MCP 서버가 같은 명령을 호출하게 만든 구조**다. 사람이 누를 수 있는 것은 에이전트도 다 할 수 있다.

README 스스로 **초기 알파이고 아직 포토샵을 대신할 수준이 아니라고** 밝힌다. 생성형 AI 기능, 빠진 도구 15개, 플러그인 호환이 가장 큰 공백이다.

## 구조

`AGENTS.md`의 작업 공간 지도 기준이다. 크레이트(Rust 패키지) 24개 이상을 층으로 나누고, `cargo xtask layers`로 아래층만 의존하는지 빌드 때 검사한다.

```
L6  ui-egui (얇은 화면)   automation (MCP 서버)
L5  engine   세션 + 명령 등록부  ← 모든 동작이 여기를 지난다
L4  io (PSD ↔ 문서)   plugins (WebAssembly 샌드박스 플러그인)
L3  compose (CPU 합성기 = 정답 기준)   gpu (wgpu 합성기)   format (.pcraft)
L2  ops paint algo text vector
L1  doc  문서 모델 (순수 데이터)
L0  geom cms color raster / psd codecs (워크스페이스 의존 없음, 단독 배포 가능)
```

- **명령이 전부다.** 새 기능은 엔진에 명령으로 등록한다. 명령마다 id, 라벨, 메뉴 경로, 단축키, 파라미터 설명, 사용 가능 여부(`enabled`), 실행 함수를 갖는다.
- **화면은 얇다.** 화면 상태도 직렬화 가능한 구조체에 두어 제어 채널이 읽고 조작할 수 있다. README의 스크린샷은 모두 이 채널로 화면 없이 렌더링했다.
- **합성기를 두 개 둔다.** CPU 합성기를 정답 기준(오라클)으로 두고, GPU 합성기 결과를 그것과 대조해 테스트한다.

## MCP 설계

`docs/mcp.md` 기준이다. 명령 500개를 MCP 도구 500개로 펼치지 않는다.

| 도구 | 역할 |
|---|---|
| `command_list` | 명령 id, 파라미터 설명, 현재 사용 가능 여부와 불가 사유(`disabledReason`)를 조회 |
| `command_run` | 명령 하나 실행 |
| `command_batch` | 명령 여러 개를 순서대로 실행. 트랜잭션이 아니라서 실패해도 앞 단계는 남는다고 명시 |
| `doc_inspect` | 레이어 트리, 이력, 선택 영역 조회 |
| `render_preview` | 결과를 PNG로 받아 눈으로 확인 (최대 2048px) |
| `ui_inspect`<br>`ui_screenshot` | 실행 중인 앱의 화면 상태 확인 |

- **조회 도구 + 범용 실행 도구 구성이다.** 에이전트는 `command_list`로 할 수 있는 일을 찾고 `command_run`으로 실행한 뒤, `doc_inspect`와 `render_preview`로 결과를 확인한다.
- **파일 접근 범위를 실행할 때 정한다.** `--automation-read-root`, `--automation-write-root`를 주지 않으면 파일을 읽고 쓰지 못한다. 경로 밖 접근, `..` 경로 이동, 심볼릭 링크 탈출은 거부한다.
- **실패 후 복구 방법을 문서에 적는다.** 배치가 중간에 실패하면 `doc_inspect`로 상태를 보고 `edit.undo`로 되돌린다. 실험은 `image.duplicate`로 사본을 만들어 그 위에서 하라고 권한다.
- 모든 도구에 제목과 MCP 주석 힌트 4종을 붙이고, 범용 실행 도구는 쓰기 가능으로 보수적으로 표시한다.
- 모르는 인자는 실행 전에 JSON-RPC `-32602`로 거부한다. 작업 스레드가 죽어도 세션은 계속 응답한다.

## 개발 규칙에서 볼 만한 것

`AGENTS.md`는 사람과 AI 에이전트가 함께 읽는 작업 지침이다.

- **절대 죽지 않는다.** 테스트가 아닌 코드에서 `unwrap`, `panic` 등을 clippy로 금지한다. 파일, 파라미터에서 온 숫자는 적대적 입력으로 다룬다. 명령을 추가하면 이상한 입력으로 패닉을 찾는 테스트(`panic_hunt`)를 돌린다.
- **측정한 숫자로 판단한다.** `docs/scorecard.md`는 성능 예산, 파일 호환 하한, 기능별 상태를 생성기로 만들고 손으로 고치지 못하게 한다. 성능 시나리오 58개 중 예산을 지킨 것은 3개뿐이라고 그대로 공개한다.
- **메뉴 연결과 동작을 구분한다.** 포토샵 메뉴 631개가 모두 명령에 연결돼 있지만, README와 `AGENTS.md` 모두 이것은 연결 여부일 뿐 동작 수준이 아니라고 밝힌다. 기능 동등성은 별도 평가 문서(`target-app-parity.md`)에서 영역별로 본다.
- **병렬 에이전트 작업 규칙이 있다.** 에이전트마다 빌드 폴더를 따로 쓰고, 새 명령은 공유 파일 대신 새 모듈에 넣고, 남의 수정으로 빌드가 깨지면 고치지 말고 기다린다.
- **다음 에이전트를 위해 개발 로그를 남긴다.** 세션이 갑자기 끝날 수 있으므로 작업을 마칠 때 무엇을 넣었고 무엇이 남았는지 기록한다.

## 한계와 주의

- **초기 알파.** README가 직접 일상 업무용 포토샵 대체가 아니라고 적는다. 성능도 대부분 예산을 넘는다 (scorecard 기준 58개 중 3개 충족, 2026-10-05 측정).
- **PSD 수치는 뜻을 구분해 읽어야 한다.** README의 "309개 중 307개"는 다시 저장해도 렌더링이 같다는 뜻이다. 포토샵이 만든 합성 이미지와 픽셀이 맞는지는 scorecard의 오라클 하한(psd-tools 309개 중 249개 이상)이 따로 있다.
- **변경이 빠르다.** 저장소 생성 2주 만에 v0.9.0이고, v0.8.2에서 이틀 뒤 v0.9.0이 나왔다.
- **별 수는 걸러 볼 것.** 생성 2주 만에 별 6만 개다. 인기 지표로 그대로 받기는 어렵다(미검증).
- Wayland에서는 파일 끌어 놓기가 안 되는 등 리눅스 환경별 제약이 README에 길게 적혀 있다.

## 가져올 수 있는 부분

| 대상 | 가져올 수 있는 부분 |
|---|---|
| 에이전트 도구 설계 (MCP) | 기능마다 도구를 만들지 않고 **조회(`command_list`) + 실행(`command_run`) + 확인(`doc_inspect`, `render_preview`)** 세 갈래로 묶는 구성. 도구 수가 늘어 모델이 도구를 잘못 고르는 문제를 줄인다. 조회 결과에 사용 불가 사유(`disabledReason`)까지 담아 에이전트가 왜 안 되는지 알게 한다 |
| 화면과 자동화의 단일 경로 | 사용자 버튼과 에이전트 호출이 같은 명령을 지나게 해, 화면에서 되는 것과 에이전트가 하는 것이 어긋나지 않게 하는 구조. Tractus 메뉴 막대 이슈에서 "창 안의 버튼과 같은 동작을 거친다"고 한 것과 같은 원칙이다 |
| 실패 복구 계약 | 배치가 트랜잭션이 아님을 명시하고, 실패 후 상태 확인 → 되돌리기 순서를 문서에 적는 방식. 액션 에이전트의 다단계 실행 실패 처리 문서에 그대로 쓸 수 있다 |
| 파일 접근 범위 | 실행할 때 읽기·쓰기 루트를 따로 받고, 없으면 파일 접근 자체를 막는 기본값 |
| 평가와 진척 관리 | 손으로 쓰지 않는 생성형 scorecard, "연결됨"과 "동작함"을 나눠 세는 방식, 내려가지 않는 하한(`FLOOR`). 평가 파이프라인 지표 관리에 그대로 적용된다 |
| 정답 기준을 둔 이중 구현 테스트 | 느리지만 단순한 CPU 구현을 정답으로 두고 빠른 GPU 구현을 대조하는 방식. 최적화한 검색이나 그래프 질의를 단순한 기준 구현과 대조하는 데 쓸 수 있다 |
| 에이전트 작업 지침 | `AGENTS.md`의 5분 안내 표, 끝내기 전 확인 명령 목록, 병렬 에이전트 규칙, 개발 로그 남기기 |
